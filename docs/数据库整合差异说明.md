> 最终：[init.sql](../backend/src/main/resources/sql/init.sql)（31 张）

## 1. 结论

| 项 | 数量 |
|---|---|
| 前端候选 | 27 |
| 原样/改名保留 | 27（全部有落点，无遗漏） |
| 合并 | 2 处（`account`→`sys_user`；`applicant`→`conversation_party`） |

## 3. 新增的表

| 表 | 为什么必须加 | 依据 |
|---|---|---|
| `profile_draft` | AI 会生成“待确认资料草稿”，不能直接写正式人员/车辆资料 | J17 |
| `confirmation` | 用户确认必须绑定目标版本、有效期和令牌，AI 不能自行确认 | J18–J21 |
| `renewal_lookup` | 续保查询是异步任务，需要保存查询状态和候选结果 | J04/J05 |
| `order_status_log` | 订单每次状态变化要可追溯操作者和时间 | 原 17 表设计 + 审计要求 |

## 4. 暂缓的表

| 候选 | 结论 | 原因 |
|---|---|---|
| `customer_salesman_relation` | 第一版不建 | `sys_user.parent_agent_id` 已能表达“客户归属业务员”。只有出现跨机构、多业务员同时授权、授权有效期时才需要独立表，已列入待确认 |
| `order_person` | 不单独建 | 订单用 `party_snapshot` + `party_versions` 固化人员，等价于订单人员表，避免重复 |
| `insurance_image` | 删除该设计 | 被 `file_object` 统一替代，避免文件表重复 |

## 5. 字段级统一

| 冲突 | 统一方案 |
|---|---|
| 前端 `role` / AI `salesperson` | `user_type` 取值 `CUSTOMER/SALESMAN/ADMIN`；`AGENT` 统一映射为 `SALESMAN` |
| 消息 `role` 小写 | 数据库 `sender_type` 大写：`USER/ASSISTANT/HUMAN_AGENT/SYSTEM` |
| 金额字符串（`"3000000.00"`） | 数据库 `DECIMAL`；接口层用字符串返回，避免 JS 浮点精度问题 |
| 前端金额「分」 | 统一为「元」，`DECIMAL(12,2)` |
| 模拟数据标记 | `data_source` = `DEMO` / `REAL`，禁止用 `is_mock=0` 冒充真实 |
| 方案状态 `pending_confirmation` | 数据库 `PENDING_CONFIRMATION` |
| 订单 `activeQuoteId` 等 | 落库为 `active_quote_id` 等 |

## 6. 与 17 表后端版本的差异

| 变化 | 表 |
|---|---|
| 新增 13 张 | `vehicle_profile`、`message_attachment`、`profile_draft`、`confirmation`、`handoff_event`、`batch_job`、`batch_job_item`、`kb_term`、`agent_session`、`audit_log`、`idempotency_key`、`renewal_lookup`、`policy_item` |
| 替换 1 张 | `insurance_image` → `file_object` |
| 人员统一 | `conversation_party` 保留并扩展，不再需要 `order_person` |
| 字段扩展 | 所有核心表补 `version`；消息补 `request_id`、`client_msg_id`；订单补 `active_*_id` |

## 7. 迁移提示

新脚本与旧库存在表结构差异（字段增加、表新增）。**不要直接在生产库执行**。本地测试建议：

1. 先备份或确认是空库
2. 新库执行 `init.sql`
3. 对比 `SHOW TABLES` 与字段差异
4. 确认无误后再考虑迁移脚本

本次未执行任何 SQL，也未删除旧表。
