# 数据库需求待确认事项

> 下面每一项都会直接影响表结构或接口，**确认前不要按其中任一方案写死代码**。
> 标记：🔴 阻塞开发　🟡 可先按建议实现，联调前确认　🟢 后续扩展

## 一、表结构类

### 1. 🔴 保单与订单是 1:1 还是 1:N
- 前端文档写 1:1，后端与 AI 契约倾向 1:N。
- 业务事实：交强险和商业险通常分别出单，同一订单可能存在两张保单。
- **当前设计**：`policy` 通过 `order_id` 支持 1:N，`policy_type` 区分 `COMPULSORY`/`COMMERCIAL`。
- 需确认：前端保单页是否按“订单下多张保单”展示；若不支持，前端列表需要调整。

### 2. 🔴 会话 stage 取值不一致
- AI：`collecting/ready/quoting/quoted/underwriting/supplement/underwriting_rejected/approved/paying/paid/issuing/issued/closed`
- 前端：`COLLECTING/RECOMMENDED/IDENTITY/READY/QUOTED/UNDERWRITING/PAYING/ISSUED/ABORTED`
- **当前设计**：采用 AI 集合（大写），并补 `CLOSED`；前端 `RECOMMENDED`、`IDENTITY`、`ABORTED` 暂未落库。
- 建议映射：`RECOMMENDED → READY`（方案已给出但未确认时用 `QUOTED` 前态）、`IDENTITY → COLLECTING`、`ABORTED → CLOSED`。
- 需确认：A 的前端状态枚举能否改为以 Java 返回值为准。

### 3. 🔴 业务员角色命名
- 前端 `AGENT`，AI/后端 `SALESMAN`。
- **当前设计**：数据库统一 `SALESMAN`。
- 需确认：前端是否统一改为 `SALESMAN`，否则由 Java 做映射。

### 4. 🟡 同一角色是否允许多人
- 当前 `conversation_party` 唯一键为 `(conversation_id, party_role, version)`，即每个角色每版本只有一人。
- 若存在“多个被保险人”“多车主”，需要改为 `(conversation_id, party_role, party_seq, version)`。
- 需确认：车险场景是否只有单个投保人/被保人/车主。

### 5. 🟡 客户与业务员授权
- 当前只靠 `sys_user.parent_agent_id`，没有授权范围、有效期、跨机构。
- 需确认：是否存在一个客户由多个业务员服务、业务员跨机构、临时授权代办。
- 若存在，二期新增 `customer_salesman_relation`。

### 6. 🟡 续保查询的数据来源
- `renewal_lookup.result_json` 只保存查询结果快照。
- 需确认：数据来自本地历史保单，还是外部平台？外部平台不可用时如何返回 `failed`。

### 7. 🟢 术语表归属
- 当前保留 `kb_term`，但 AI 文档说明第一版可继续用 C 本地词库。
- 需确认：术语由 Java 维护还是 C 维护；若 C 维护，`kb_term` 可暂不启用。

## 二、字段与格式类

### 8. 🔴 金额单位与返回格式
- 数据库：`DECIMAL(12,2)`，单位元。
- 接口文档仍有“单位：分”。
- 建议：后端统一返回字符串（如 `"3560.00"`），前端不做除法。
- 需确认：A 是否接受字符串金额；C 的 `PlanItem` 金额格式是否同步。

### 9. 🔴 确认令牌由谁签发
- 当前 `confirmation.token_hash` 只存哈希。
- AI 文档要求：令牌只在 B 面向已认证用户签发，AI 上下文不返回。
- 需确认：J18（创建确认）是否返回令牌；J20（确认）是否必须带令牌。

### 10. 🟡 消息顺序如何保证
- `chat_message` 有 `(conversation_id, seq)` 唯一约束。
- 高并发下需要 Redis `INCR` 取号或数据库重试。
- 需确认：Redis 是否作为唯一取号来源（项目已引入 Redis）。

### 11. 🟡 OCR 字段 JSON 的 key 规范
- `ocr_record.fields_json` 目前是自由 JSON。
- 需与 C 确认：行驶证、身份证正反面各有哪些 key、置信度字段、异常标记字段。

### 12. 🟡 文件类型与大小限制
- 当前 `file_object` 支持图片、视频、PDF 元数据。
- 需与 C 确认：OCR 支持哪些格式；验车视频大小上限；是否需要缩略图 key。

### 13. 🟡 支付状态枚举
- 前端：`PENDING/PAID/FAILED/REFUNDED`
- AI：`pending/success/failed/closed/refunded`
- 数据库：`CREATED/PENDING/SUCCESS/FAILED/CLOSED/REFUNDED`
- 需确认：前端是否接受 `SUCCESS` 而非 `PAID`；`CLOSED` 是否展示。

## 三、流程与权限类

### 14. 🔴 报价与核保由谁推进
- AI 文档建议：C 发起首次报价/核保，B 后台任务负责异步更新和自动核保。
- 需确认：第一版是否只做同步 Mock；同步时 C 是否直接调用 J33。

### 15. 🔴 批量办理的授权模型
- 当前 `batch_job_item` 只记录 customer_id，没有逐客户授权快照。
- 需确认：业务员批量操作前，是否需要校验并记录 `parent_agent_id` 归属；跨客户批量上限 30 是否保留。

### 16. 🟡 人工工单状态
- 前端：`REQUESTED/QUEUED/SERVING/CLOSED`
- AI：`pending/accepted/resolved/cancelled`
- 数据库：`PENDING/ACCEPTED/RESOLVED/CANCELLED`
- 需确认：是否保留排队位次（`queue_position`）与“已取消”。

### 17. 🟡 订单快照的字段范围
- 当前 `vehicle_snapshot`、`party_snapshot`、`plan_snapshot` 为 JSON。
- 需确认：快照是否需要包含加密证件号，还是只保存脱敏值。
- 建议：快照只存脱敏值 + 原资料版本号，完整证件仍通过 `conversation_party` 受控读取。

### 18. 🟢 审计日志保留期
- `audit_log` 只追加。
- 需确认：保留多久；是否需要按月归档；日志中哪些字段必须脱敏。
