## 一、必须优先统一（会直接影响接口联调）

### 1. 金额单位冲突：分 vs 元

- **现状**：`docs/接口文档.md` 写的是"金额单位：**分（整数）**"，本次要求是 `DECIMAL(12,2)`、单位**元**。
- **当前处理**：数据库按 `DECIMAL(12,2)` 元设计。
- **建议**：以"元 + 两位小数"为准，同步修改接口文档；后端返回金额用**字符串**（如 `"3850.00"`），避免 JS 浮点误差。
- **需确认**：A（前端）、C（AI 工具参数）。

### 2. 会话阶段（stage）枚举

- **现状**：接口文档写 `COLLECTING_INFO / RECOMMENDING / ID_UPLOAD / QUOTING / UNDERWRITING / PAYING / POLICY_ISSUED`，并标注"命名待确认"。
- **当前处理**：沿用这套命名。
- **建议**：定稿后写进接口文档，前端只做展示映射。

### 3. 订单状态（status）枚举

- **当前处理**：`CREATED / QUOTING / QUOTED / UNDERWRITING / UNDERWRITTEN / PENDING_PAYMENT / PAID / ISSUING / ISSUED / FAILED / CANCELLED`。
- **待确认**：是否与前端页面状态、AI 工具返回值一致；是否需要 `NEED_MATERIAL`（目前放在核保状态里）。

## 二、表结构层面的取舍

### 4. 手机号唯一 + 逻辑删除的冲突

- **问题**：`sys_user.phone` 唯一，用户逻辑删除后同一手机号无法再注册。
- **建议**：注销时把手机号改写为 `原号码__deleted__时间戳`；或改用 `status=DELETED` 不做逻辑删除。
- **需确认**：产品是否要求"注销后可用原手机号重新注册"。

### 5. 车牌号 / VIN 是否唯一

- **当前处理**：只建普通索引。
- **原因**：车辆可能过户、换牌，历史记录要保留；OCR 也可能识别错误。
- **建议**：VIN 建唯一索引（允许 NULL）；车牌按 `(owner_user_id, plate_no)` 唯一。
- **需确认**：业务是否允许同一车牌存在多条历史记录。

### 6. 是否需要 `policy_item`（保单险种明细表）

- **当前处理**：保单险种明细放在 `policy.details` JSON。
- **风险**：无法直接用 SQL 按险种统计保费、核对保额。
- **建议**：如果要做"保单险种对账"或"按险种统计"，二期拆 `policy_item`。**首版可不加。**

### 7. 是否需要 `idempotency_record`（幂等记录表）

- **当前处理**：靠 `order_no`、`quote_no`、`payment_no` 唯一索引 + 请求参数校验防重。
- **风险**：同一请求网络重试时，无法返回"首次执行结果"，只能报"已存在"。
- **建议**：首版可接受；若要求"重复请求返回原结果"，二期加幂等表（Redis 只适合短期，重启会丢）。

### 8. 批量操作没有表承载

- **现状**：`docs/接口文档.md` 4.11 有"业务员端（批量操作）"接口。
- **当前处理**：第一版 17 表**不含** `batch_job` / `batch_job_item`，批量操作暂无法落库。
- **建议**：要么本期补 2 张表（共 19 张），要么明确批量功能放到第二版。
- **需确认**：批量操作是否属于首版验收范围。

### 9. 业务员代客办理的授权关系

- **当前处理**：只靠 `conversation.salesman_id` 表示"谁在接待"，没有独立的授权表。
- **风险**：无法表达"业务员可代该客户报价/支付/出单"的授权范围与有效期。
- **建议**：首版由业务规则限制（只有被分配的会话可操作）；二期加 `customer_salesman_relation`。

### 10. 保险公司 / 险种目录表

- **当前处理**：方案明细、报价明细直接存 `coverage_code/coverage_name`，报价和保单直接存 `insurer_code/insurer_name`。
- **风险**：险种名称改名后，历史数据是对的（快照），但新方案容易写错编码。
- **建议**：二期加 `insurer`、`insurance_coverage` 目录表做校验；首版在 Service 层用常量枚举约束。

### 11. 是否需要 `request_record`（AI 请求链路表）

- **当前处理**：`chat_message.request_id` 记录请求 ID，没有独立表。
- **风险**：AI 说"已下单"但数据库没有时，排查手段有限。
- **建议**：首版先靠日志；若要做可观测性，二期加表。

## 三、安全与运维

### 12. 加密算法与密钥

- **当前处理**：身份证号、发动机号用 AES-256-GCM 存 `VARBINARY(512)`，另有 HMAC-SHA256 用于精确查询。
- **待确认**：密钥放哪（环境变量 `PII_AES_KEY` / `PII_HMAC_KEY`），由谁保管。
- **限制**：加密后**不能模糊搜索**身份证号，只能精确匹配。

### 13. 文件存储方式

- **当前处理**：`insurance_image.file_url` 存地址或对象 key，二进制不入库。
- **待确认**：第一版用本地目录还是 MinIO/OSS？地址是绝对 URL 还是相对 key？

### 14. 数据保留与清理

- **待确认**：聊天消息、OCR 记录、状态日志保留多久？是否需要归档表？
- **建议**：首版全部保留，不做删除；后续按需加归档策略。
