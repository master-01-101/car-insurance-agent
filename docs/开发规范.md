# 开发规范 — 车险出单智能体

> 本文是团队协作的**硬性约定**,目的是避免分支互相覆盖、接口对不上、密钥泄露。
> 标 ⚠️ 的条目需团队确认后执行;未标注的是已确定规则。

---

## 1. 团队与职责

| 成员 | 角色 | 负责范围 | 工作分支 |
| --- | --- | --- | --- |
| 你 | 组长 / Java 后端 | 后端 API、数据库、状态机、分支与 PR 审核 | `feature/backend` |
| 成员 A | 前端 | 用户端、业务员端页面与交互 | `feature/frontend` |
| 成员 C | AI 智能体 | 对话编排、OCR、RAG、人工转接 | `feature/agent` |

**组长额外职责:** 审核并合并 PR、维护 `dev` 质量、协调接口变更。

## 2. Git 分支规范

### 2.1 分支模型

```text
main           生产/稳定分支,只接受来自 dev 的合并
 └── dev       集成分支,所有人通过 PR 合入
      ├── feature/backend
      ├── feature/frontend
      └── feature/agent
```

### 2.2 硬性规则

| 规则 | 说明 |
| --- | --- |
| ❌ 禁止直接 push `main` | 任何提交都必须经过 PR |
| ❌ 禁止直接 push `dev` | 必须从 `feature/*` 发起 PR,经组长审核 |
| ✅ 只能直接 push 自己的 `feature/*` | 不得推送别人的功能分支 |
| ✅ PR 目标分支只能是 `dev` | `dev → main` 由组长在阶段验收时发起 |
| ❌ 禁止自动合并 PR | 由组长人工审核后合并 |
| ❌ 禁止 `git push --force` 到 `main` / `dev` | 公共分支不可改写历史 |
| ✅ 合并前先同步 `dev` | 保持分支最新,减少冲突 |
| ✅ 冲突在本地解决 | 不得让远端处于半合并状态 |

### 2.3 分支命名

- 功能分支:`feature/<模块>`,当前固定为 `feature/backend`、`feature/frontend`、`feature/agent`。
- 临时修复(如确需):`fix/<简述>`,完成后删除。
- 名字一律小写,用 `/` 分层,禁止中文和空格。

### 2.4 日常流程(以你为例)

```bash
# 1. 切到自己的分支
git checkout feature/backend

# 2. 拉取最新 dev(同步别人的改动)
git fetch origin
git merge origin/dev        # 或团队统一用 rebase,⚠️ 需统一选一种

# 3. 开发并提交
git add <具体文件>
git commit -m "feat(order): 新增订单状态查询接口"

# 4. 推送自己的分支
git push origin feature/backend

# 5. 到 GitHub 创建 PR:feature/backend → dev
# 6. 由组长审核,人工合并;不自动合并
```

> ⚠️ 团队需统一同步方式:`git merge origin/dev` 还是 `git rebase origin/dev`。**新手建议用 merge**,冲突处理更直观。

## 3. Commit 规范

采用 **Conventional Commits**,格式:

```text
<type>(<scope>): <subject>
```

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档 |
| `style` | 格式调整(不影响逻辑) |
| `refactor` | 重构 |
| `test` | 测试 |
| `chore` | 构建、依赖、工具配置 |
| `perf` | 性能优化 |

**scope 建议:** `backend`、`frontend`、`agent`、`docs`、`db`。

**要求:**

- 一句话说清「做了什么」,不超过 50 字。
- 一次提交只做一件事,不要把多个功能混在一个 commit。
- 禁止 `update`、`fix bug`、`111` 这类无意义信息。
- 涉及接口/表结构变更,在正文中说明影响范围。

**示例:**

```text
feat(backend): 新增会话创建与消息查询接口
fix(backend): 修复报价重复提交未拦截的问题
docs(docs): 补充接口错误码说明
chore: 增加根目录 .gitignore
```

## 4. API 命名规范

### 4.1 路径

| 规则 | 示例 |
| --- | --- |
| 统一前缀 `/api/v1` | `/api/v1/orders` |
| 资源用**复数名词** | `/orders`、`/sessions`、`/policies` |
| 层级不超过 3 层 | `/orders/{orderId}/plans` |
| 路径小写,多词用连字符 | `/under-writings`(更推荐 `underwritings`)⚠️ 待统一 |
| 动作型接口用子资源表达 | `POST /orders/{id}/payments` |
| 避免动词 | ❌ `/getOrders` ✅ `GET /orders` |

### 4.2 HTTP 方法

| 方法 | 用途 | 幂等 |
| --- | --- | --- |
| GET | 查询 | 是 |
| POST | 创建 | 否(需幂等键) |
| PUT | 全量更新 | 是 |
| PATCH | 部分更新 | 是 |
| DELETE | 删除 | 是 |

### 4.3 字段与状态

- JSON 字段:**camelCase**;数据库:**snake_case** ✅。
- 枚举值:**大写英文 + 下划线**,如 `PENDING`、`POLICY_ISSUED`。
- 金额:整数「分」,字段名带 `Cent` 或文档注明单位 ⚠️ 待统一。
- 时间:ISO-8601,带时区。
- 布尔字段用 `isXxx` / `needXxx` / `mock`。

### 4.4 返回与错误

- 统一返回结构 `{ code, message, data, traceId }`,见 `docs/接口文档.md` ✅。
- `code=0` 表示成功,业务错误码不得与 HTTP 状态码混用 ✅。
- 错误提示面向用户,不暴露堆栈、SQL、内部路径 ✅。
- 前端只能依据 `code` 判断业务结果,不能匹配 `message` 文案 ✅。

### 4.5 安全

- 身份证号、手机号返回必须脱敏 ✅。
- 接口鉴权由服务端判定角色,前端隐藏按钮不等于有权限 ✅。
- 对外部系统的调用全部封装 Adapter,模拟结果必须带 `mock=true` ✅。
- 禁止在 URL 中传递身份证号、密钥等敏感参数 ✅。

## 5. 目录规范

### 5.1 仓库根目录

```text
car-insurance-agent/
├─ backend/     Java 后端
├─ agent/       Python 智能体
├─ frontend/    前端(由成员 A 维护)
├─ docs/        项目文档
├─ sql/         建表与初始化脚本(建议放 backend/sql,⚠️ 待确认)
├─ .gitignore
└─ README.md(根级,⚠️ 待补)
```

> 根目录不放业务代码;每个模块的启动方式写在自己模块的 `README.md` 里。

### 5.2 后端

```text
backend/src/main/java/<根包>/
├─ common/      # 统一返回、异常、错误码、常量
├─ config/
├─ controller/  # 只做参数接收/校验/返回
├─ service/     # 业务逻辑与状态机
├─ mapper/
├─ entity/
├─ dto/
├─ converter/
├─ client/      # AI 调用、第三方 Adapter
└─ security/
```

- Controller 不写业务逻辑,不直接操作 Mapper ✅。
- Entity 不直接返回给前端,必须转 DTO ✅。
- 配置中的密钥用环境变量占位,`application.yml` 只放非敏感默认值 ✅。

### 5.3 前端

- 已由成员 A 建立结构,以其 `frontend/README.md` 与 `AGENTS.md` 为准 ✅。
- 接口统一收在 `src/api/`,页面组件不得散落硬编码 URL ✅。
- 不伪造后端数据;未实现能力使用统一占位符 ✅。

### 5.4 智能体

- 结构见 `agent/README.md`;密钥只放环境变量 ✅。
- 不直连业务数据库,业务数据通过后端内部接口获取 ✅。

## 6. PR(Pull Request)规范

### 6.1 基本要求

| 要求 | 说明 |
| --- | --- |
| 目标分支 | 只能是 `dev` ✅ |
| 来源分支 | 自己的 `feature/*` ✅ |
| 大小 | 单次 PR 尽量 < 500 行;大功能拆成多个 PR ⚠️ |
| 标题 | 与主要 commit 一致,如 `feat(backend): 订单状态查询接口` |
| 描述 | 说明改了什么、为什么、如何验证、影响哪些接口/表 |
| 审核 | 至少 1 人审核(组长),复杂改动 2 人 ⚠️ |
| 合并 | **人工合并**,禁止自动合并 ✅ |
| 合并后 | 删除已合并的功能分支(可选)⚠️ |

### 6.2 PR 描述模板

```markdown
## 改动内容
- 新增 xxx 接口
- 修改 xxx 表结构

## 为什么改
（关联需求 / 修复的问题）

## 如何验证
1. 启动后端
2. 调用 GET /api/v1/orders/1/status
3. 期望返回 ...

## 影响范围
- 接口:新增 / 修改 xxx
- 数据库:新增 xxx 字段
- 需要其他成员配合:是 / 否

## 自查清单
- [ ] 本地能编译 / 启动
- [ ] 接口与 docs/接口文档.md 一致
- [ ] 表结构与 docs/数据库设计.md 一致
- [ ] 未提交 .env、密钥、IDE 配置
- [ ] 已同步最新 dev
```

### 6.3 审核要点

- 是否直接改 `main` / `dev` ✅。
- 是否提交了密钥、`.env`、`node_modules`、`target` ✅。
- 接口字段、错误码是否与文档一致 ✅。
- 是否有伪造外部系统结果(必须带 `mock=true`)✅。
- 是否破坏已有接口(需升版本或兼容)✅。

## 7. 代码风格

| 模块 | 规范 | 状态 |
| --- | --- | --- |
| Java | 阿里巴巴 Java 开发手册;4 空格缩进;类名大驼峰;方法名小驼峰 | ✅ |
| Java | 使用 Lombok?`@Data` 是否允许 | ⚠️ 待确认(建议 DTO 可用) |
| Python | black 格式化 + ruff 检查;4 空格;snake_case | ⚠️ 建议 |
| TypeScript | 沿用前端现有 ESLint / Prettier 配置 | ✅ |
| 注释 | 对外接口、复杂业务逻辑写注释;不写无意义注释 | ✅ |
| 日志 | 用 SLF4J,禁止 `System.out.println`;不打印身份证、token、密钥 | ✅ |

## 8. 密钥与配置

| 规则 | 说明 |
| --- | --- |
| `.env` 一律不入库 | 已加入 `.gitignore` ✅ |
| 只提交 `.env.example` | 写清变量名和示例值,不带真实密钥 ✅ |
| 数据库口令、AI Key、支付密钥、加密密钥 | 全部环境变量注入 ✅ |
| 误提交密钥 | 立即更换密钥并通知组长,不能只删文件 ✅ |
| 本地配置 | 用 `application-local.yml` 等,不入库 ✅ |

## 9. 测试与联调

- 后端:Service 层写单元测试;接口用 Swagger / Postman 验证 ✅。
- 前端:未实现能力用占位符,不得造假数据 ✅。
- AI:工具调用需有 Mock 模式,便于无外部服务时联调 ⚠️。
- 联调前先对照 `docs/接口文档.md` 逐项确认字段 ✅。
- 任何人修改接口/表结构,必须**先改文档、再改代码、并通知两端** ✅。
