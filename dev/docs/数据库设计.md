# 数据库设计 — 车险出单智能体（整合版 v2）

> 版本：v2.0（31 张表）
> 脚本：[init.sql](../backend/src/main/resources/sql/init.sql)
> 上一版 17 表设计已归档：[数据库设计_17表_v1.md](archive/数据库设计_17表_v1.md)

## 1. 为什么是 31 张表

三份资料各自的表清单并不一致：

| 来源 | 表数 | 特点 |
|---|---|---|
| 前端候选设计 | 27 | 覆盖确认、草稿、批量、术语、审计 |
| AI → Java 契约 | 引用 13 类对象 | 明确要求 `confirmation`、`profile_draft`、`renewal_lookup` |
| 后端 17 表设计 | 17 | 核心业务完整，缺确认/草稿/续保/术语/批量 |

整合后 31 张，不是把三份清单相加，而是按“业务实体唯一”原则合并（详见[数据库整合差异说明.md](数据库整合差异说明.md)）。

## 2. 全局约定

| 项 | 约定 |
|---|---|
| 引擎 / 字符集 | InnoDB / `utf8mb4` / `utf8mb4_0900_ai_ci` |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` |
| 金额 | `DECIMAL(12,2)`，单位元；保额 `DECIMAL(14,2)` |
| 未知金额 | 存 `NULL`，不能写 0 |
| 时间 | `DATETIME`，`created_at` 默认当前时间 |
| 状态 | `VARCHAR` 大写常量，不用 ENUM |
| 关联 | 只建索引，不建物理外键（避免循环依赖、便于分库） |
| 删除 | 主数据用 `deleted` 逻辑删除；订单/保单/日志类只追加不删除 |
| 模拟数据 | `data_source` = `DEMO` / `REAL`，禁止把 DEMO 当真实结果 |
| 敏感信息 | 证件号、发动机号加密 + 哈希 + 脱敏三列分开 |

## 4. 状态机

### 4.1 会话 stage

```
COLLECTING → READY → QUOTING → QUOTED → UNDERWRITING → APPROVED
     ↑          ↑                              │
     └──────────┴──── SUPPLEMENT ←─────────────┘
                         │
             UNDERWRITING_REJECTED → CLOSED
APPROVED → PAYING → PAID → ISSUING → ISSUED → CLOSED
任意阶段 → CLOSED / ABORTED
```

- `READY` 表示“资料 + 方案都已确认”，不是确认任意一个字段。
- `handling_mode` 独立表示人工接管（`AI`/`HUMAN`），不覆盖 `stage`。
- 前端旧阶段 `RECOMMENDED`/`IDENTITY` 映射见[数据库需求待确认.md](数据库需求待确认.md)。

### 4.2 订单状态

`DRAFT → QUOTING → QUOTED → UNDERWRITING → NEED_MATERIAL / REJECTED / APPROVED → PAYING → PAID → ISSUING → ISSUED → CANCELLED`

| 迁移 | 触发条件 |
|---|---|
| DRAFT → QUOTING | 用户明确发起报价（J28/J31） |
| QUOTING → QUOTED | 报价成功且金额完整 |
| QUOTED → UNDERWRITING | 报价成功且未过期（J33） |
| UNDERWRITING → NEED_MATERIAL | 核保要求补件 |
| NEED_MATERIAL → UNDERWRITING | 补件后重提（新核保记录） |
| UNDERWRITING → APPROVED | 核保通过 |
| UNDERWRITING → REJECTED | 核保拒绝 |
| APPROVED → PAYING | 创建支付单（J36） |
| PAYING → PAID | 后端验签/查单确认，不接受前端或 AI 声明 |
| PAID → ISSUING → ISSUED | 出单成功并落保单 |
| 任意未支付状态 → CANCELLED | 用户取消或业务终止；已支付订单不可直接取消 |

### 4.3 其他状态

| 表 | 状态 |
|---|---|
| `insurance_plan` | `DRAFT → PENDING_CONFIRMATION → CONFIRMED`；旧版本转 `SUPERSEDED`；可 `CANCELLED` |
| `quote_record` | `PROCESSING → SUCCEEDED / FAILED / EXPIRED` |
| `underwriting_record` | `PROCESSING → PASSED / REJECTED / NEED_MATERIAL` |
| `payment_record` | `CREATED → PENDING → SUCCESS / FAILED / CLOSED`；`SUCCESS → REFUNDED` |
| `handoff_task` | `PENDING → ACCEPTED → RESOLVED`；`PENDING/ACCEPTED → CANCELLED` |
| `batch_job` | `PENDING → RUNNING → COMPLETED / PARTIAL_FAILED / FAILED` |
| `confirmation` | `PENDING → CONFIRMED / EXPIRED / SUPERSEDED / CANCELLED` |

## 5. 关键设计说明

### 5.1 为什么方案要“只追加”

方案修改必须插入新行（`version + 1`），旧行改为 `SUPERSEDED`。订单通过 `plan_id + plan_version` 固定引用，历史订单不会被新方案污染。

### 5.2 为什么订单存三份快照

`vehicle_snapshot`、`party_snapshot`、`plan_snapshot` 保存下单时的完整数据。客户之后改手机号、改保额，都不影响已下单记录。

### 5.3 为什么人员只有一张表

`conversation_party` 用 `party_role` 区分 `APPLICANT`/`INSURED`/`VEHICLE_OWNER`，按 `version` 版本化。前端 `applicant`、后端 `order_person` 都不再单独建表：

- 一份资料 = 一行，避免三张表字段重复
- 订单侧用 `party_snapshot` + `party_versions` 固化，等价于 `order_person`
- 避免同一人同时是投保人和车主时维护多份数据

### 5.4 敏感字段三列法

| 列 | 用途 |
|---|---|
| `*_enc` | AES-256-GCM 密文，仅后端解密 |
| `*_hash` | HMAC-SHA256，用于查重/索引，不可逆 |
| `*_masked` | 展示值，如 `3301**********1234` |

普通查询、列表、日志、AI 上下文只能使用 `masked`。

### 5.5 JSON 的使用边界

允许 JSON：OCR 字段、方案条款、订单快照、展示数据、补件要求、批量错误详情。
不允许：订单金额、订单状态、人员证件号、方案险种列表（这些必须独立成列/表，便于查询与校验）。

### 5.6 确认与版本

`confirmation` 同时保存 `target_id` + `target_version`，并在确认时校验版本。方案一旦升版，旧确认立即 `SUPERSEDED`，避免“确认了过期方案”。

### 5.7 幂等

`idempotency_key` 保存 `idem_key`、请求指纹和首次结果：

- 相同 key + 相同指纹 → 返回原结果
- 相同 key + 不同指纹 → `IDEMPOTENCY_CONFLICT`

支付另用 `payment_record.out_trade_no` 唯一约束兜底，防重复扣款。

## 6. 索引策略

| 场景 | 索引 |
|---|---|
| 登录 | `uk_sys_user_username` |
| 客户车辆列表 | `idx_vehicle_owner` |
| 会话列表 | `idx_conversation_customer (customer_id, last_message_at)` |
| 聊天分页 | `uk_chat_message_seq (conversation_id, seq)` |
| 业务员工单池 | `idx_handoff_queue (status, requested_at)` |
| 订单查询 | `uk_insurance_order_no`、`idx_insurance_order_customer` |
| 支付回调 | `uk_payment_out_trade_no`、`idx_payment_transaction` |
| 审计追溯 | `idx_audit_resource`、`idx_audit_trace` |
