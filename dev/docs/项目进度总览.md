## 1. 一句话说清项目

用户通过**对话**完成车险从「收集信息」到「出保单」的全流程：上传行驶证 → OCR 识别 → AI 推荐方案 → 自然语言改方案 → 上传身份证 → 报价 → 核保 → 支付 → 生成保单。业务员端额外支持**批量办理**与**人工接管**。

### 三个模块、三个人

| 模块 | 目录 | 负责人 | 技术栈 | 职责 |
|---|---|---|---|---|
| 前端 | `frontend/` | 成员 A | Vue 3 + TS + Vite | 用户端 / 业务员端页面，只调 `/api`，不直连 AI |
| 后端 | `backend/` | **我（B）** | Java 21 + Spring Boot 3.5.x + MyBatis-Plus + MySQL + Redis | 鉴权、业务 API、状态机、落库、调用 AI、第三方 Mock |
| 智能体 | `agent/` | 成员 C | Python + FastAPI + LangGraph | 多轮对话、方案推荐与修改、OCR 编排、RAG 术语 |

### 三条铁律（AI 与新对话必须知道）

1. **我只改 `backend/` 和 `docs/`**，不碰 `frontend/`、`agent/`。
2. **后端是状态的唯一权威**。报价、核保、支付、保单结果只认服务端返回，前端和 AI 不得自行判定。
3. **当前没有接任何真实保险公司 / 支付 / 人工平台**，全部是 Mock，必须带 `mock=true` 标识，不能对外宣称已接入。

## 2. 请求链路

```text
浏览器 ──/api/*──> Java 后端（鉴权 / 校验 / 落库 / 状态机 / 审计）
                      │
                      ├──> MySQL 8.0（业务数据，31 张表）
                      ├──> Redis（token / 幂等键 / 消息取号）
                      └──> FastAPI 智能体（内部调用，带 X-Internal-Token）
                                  │
                                  └──> OCR · 方案生成 · RAG 术语
```

要点：前端**只认一个网关** `/api`，不直连 FastAPI；智能体**不直连数据库**，所有读写都调后端。

## 3. 七阶段流程与数据落点

| 阶段 | 用户动作 | 关键接口 | 主要表 |
|---|---|---|---|
| ① 收集信息 | 传行驶证正副页 / 输车牌查续保 | `/api/files`、`/api/ocr/license`、`/api/vehicles/lookup` | `file_object`、`ocr_record`、`vehicle`、`vehicle_profile` |

| ④ 报价 | 点报价，看保费 | `/api/quotations`、`/api/quotations/{id}` | `insurance_order`、`quote_record`、`quote_item` |

### 6.1 两个实例都已就绪

### 6.2 31 张表分组

| 分组 | 表 |
|---|---|
| 身份与车辆 | `sys_user`、`vehicle`、`vehicle_profile` |
| 会话与文件 | `conversation`、`chat_message`、`message_attachment`、`file_object`、`ocr_record` |
| 人员与确认 | `conversation_party`、`profile_draft`、`confirmation` |

| 报价 / 核保 / 支付 / 保单 | `quote_record`、`quote_item`、`underwriting_record`、`underwriting_material`、`payment_record`、`policy`、`policy_item` |
| 运营 | `batch_job`、`batch_job_item`、`handoff_task`、`handoff_event` |
| 辅助 | `kb_term`、`agent_session`、`audit_log`、`idempotency_key`、`order_status_log`、`renewal_lookup` |

### 6.3 写代码必须遵守的 6 条约定

1. 主键 `BIGINT UNSIGNED AUTO_INCREMENT`，**对外 ID 用 ULID 字符串**（26 位），两者靠唯一键绑定。
2. 金额 `DECIMAL(12,2)`，单位**元**；未知金额存 `NULL`，**不能写 0**。
3. 状态一律 `VARCHAR` 大写常量；状态流转只在 Service 层裁决。
4. **不建物理外键**，关联完整性由 Service 层校验。
5. 敏感字段三列法：`*_enc`（AES-256-GCM）+ `*_hash`（HMAC-SHA256 查询用）+ `*_masked`（展示用）。**明文永不入库、永不返回**。
6. 模拟数据用 `data_source = DEMO / REAL` 标识。

### 6.4 三个设计取舍（别被旧文档带偏）

- **保单是 1:N**：一个订单可能出交强险、商业险两张保单，`insurance_order` 没有 `policy_id` 单值字段。
- **方案只追加版本**：改方案不改旧行，新增 `version` + `previous_plan_id`；订单锁定 `plan_id + plan_version`。
- **订单存三份快照**：`vehicle_snapshot`、`party_snapshot`、`plan_snapshot`（JSON），保证历史不被后续修改污染。

## 7. 待确认清单（开发前必须拍板）

详见 [数据库需求待确认.md](数据库需求待确认.md)（18 项）。最关键的 4 个 🔴 阻塞项：

| # | 问题 | 当前库里的做法 | 需要谁定 |
|---|---|---|---|
| 1 | 保单与订单 1:1 还是 1:N | 按 1:N 设计，`policy_type` 区分交强/商业 | A（前端保单页能否展示多张） |
| 2 | 会话 `stage` 枚举三套不一致 | 采用 AI 的大写集合 | A + C |
| 3 | 业务员角色叫 `AGENT` 还是 `SALESMAN` | 库里统一 `SALESMAN` | A（是否改，或由 Java 映射） |
| 4 | 金额单位与格式 | 库里按元（DECIMAL 12,2） | A + C（是否接受字符串 `"3560.00"`） |

其余较重要：确认令牌由谁签发、报价/核保谁推进（C 发还是 B 后台任务）、批量操作授权模型、消息 seq 是否用 Redis 取号、支付状态 `SUCCESS` vs `PAID`。

## 9. 下一步计划（建议顺序）

```text
1. 建 Maven 工程骨架        pom.xml + CarInsuranceApplication + application.yml(dev/prod)
2. 接 MySQL + Redis + MyBatis-Plus  连通性自测，一个健康检查接口
3. 统一返回与异常           Result<T>{code,message,data,errorCode,requestId} + 全局异常处理
4. Entity + Mapper          先做 sys_user / vehicle / conversation 三张
5. 登录注册 + JWT + Redis   BCrypt 存密码，token 放 Redis，打通 /api/auth/login
6. 会话 API                 GET/POST /api/conversations，验证权限与分页
7. 再按七阶段逐个推进       文件上传 → OCR → 方案 → 报价 → 核保 → 支付 → 保单
```

原则：**每步都能跑通、能自测，再进下一步**；先同步 Mock，异步/SSE 留二期。
