## 1. 设计原则

### 1.1 为什么用「逻辑外键」

本项目**不建 `FOREIGN KEY` 约束**，只在关联字段上建普通索引，关联完整性由 Java Service 层校验：

1. 首版表少、迭代快，物理外键会增加测试数据构造和改表的成本；
2. 业务记录（订单、保单、消息）只追加不删除，外键的级联/限制没有实际收益；
3. 主数据表使用逻辑删除（`deleted`），物理外键与之语义冲突。

**代价**：删除或修改父数据前，Service 必须先查询子表是否被引用。

### 1.2 金额与时间

| 项目 | 约定 |
| --- | --- |
| 保费、金额 | `DECIMAL(12,2)`，单位**元**，两位小数 |
| 保额 | `DECIMAL(14,2)`（三者险保额可能上千万） |
| 未知金额 | 存 `NULL`，**禁止用 0 冒充** |
| 时间 | `DATETIME`；`created_at` 默认当前时间，`updated_at` 自动更新 |

> 注意：现有 `docs/接口文档.md` 写的是"金额单位：分（整数）"，与本设计冲突。
> 以本次要求 `DECIMAL(12,2)` 元为准，接口文档需要同步修改（见待确认事项）。

### 1.3 其他约定

- 主键：`BIGINT UNSIGNED AUTO_INCREMENT`
- 业务编号：独立字段 + 唯一索引（`order_no`、`quote_no`、`payment_no`、`policy_no`、`task_no`）
- 状态：`VARCHAR` + 应用层枚举，不用数据库 `ENUM`
- 并发：可变业务表带 `version INT`，配合 MyBatis-Plus 乐观锁
- 删除：主数据用 `deleted` 逻辑删除；业务流水只改状态
- 命名：小写下划线，全部字段加反引号，避开 MySQL 保留字

## 3. 逐表设计

> 除特殊说明外，所有表都含 `created_at`、`updated_at`，下文不再重复。

### 3.1 `sys_user` 用户表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | PK |
| phone | VARCHAR(20) | 登录手机号，**唯一** |
| password_hash | VARCHAR(100) | BCrypt 哈希，禁止明文 |
| user_type | VARCHAR(20) | `CUSTOMER` / `SALESMAN` / `ADMIN` |
| real_name | VARCHAR(50) | 真实姓名 |
| email / avatar_url | VARCHAR | 可选资料 |
| status | VARCHAR(20) | `ACTIVE` / `DISABLED` / `LOCKED`，默认 `ACTIVE` |
| last_login_at | DATETIME | 最近登录 |
| deleted | TINYINT | 逻辑删除 |

**索引**：`uk_sys_user_phone(phone)`、`idx_sys_user_type_status(user_type,status)`。

**设计理由**：三种角色共用一张表，登录、密码、状态逻辑只写一份；角色差异通过 `user_type` 区分，避免三套登录代码。

### 3.2 `vehicle` 车辆资料表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | PK |
| owner_user_id | BIGINT UNSIGNED | 车主 |
| plate_no | VARCHAR(16) | 车牌号 |
| vin | VARCHAR(32) | 车架号 |
| engine_no_cipher | VARBINARY(512) | 发动机号密文（敏感） |
| engine_no_masked | VARCHAR(32) | 发动机号脱敏值 |
| vehicle_type / brand_model | VARCHAR | 车辆类型、品牌型号 |

| usage_type | VARCHAR(20) | `NON_OPERATING` / `OPERATING` |
| source | VARCHAR(20) | `OCR` / `NEW` / `MANUAL` |
| status | VARCHAR(20) | `ACTIVE` / `INACTIVE` |
| version / deleted | INT / TINYINT | 乐观锁、逻辑删除 |

**索引**：`owner_user_id`、`plate_no`、`vin`。

**设计理由**：发动机号属于敏感信息，存密文 + 脱敏值，列表页只展示脱敏值。

### 3.3 `conversation` 会话表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | PK |
| customer_id | BIGINT UNSIGNED | 客户 |
| salesman_id | BIGINT UNSIGNED | 业务员，可空 |
| vehicle_id | BIGINT UNSIGNED | 车辆，可空 |

| last_message_at | DATETIME | 最后消息时间 |


### 3.4 `chat_message` 聊天消息表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | PK |
| conversation_id | BIGINT UNSIGNED | 会话 |
| seq | INT | 会话内序号，从 1 递增 |
| sender_type | VARCHAR(20) | `USER` / `ASSISTANT` / `HUMAN_AGENT` / `SYSTEM` |
| content_type | VARCHAR(20) | `TEXT` / `IMAGE` / `CARD` / `FILE` |
| content | MEDIUMTEXT | 文本内容 |
| metadata | JSON | 卡片、工具调用等结构 |
| image_id | BIGINT UNSIGNED | 关联材料 |
| client_message_id | VARCHAR(64) | 前端幂等 ID |
| request_id | VARCHAR(64) | 请求追踪 ID |

**唯一约束**：
- `uk_chat_message_seq(conversation_id, seq)` —— 保证顺序不重复
- `uk_chat_message_client(conversation_id, client_message_id)` —— 防重复发送

**设计理由**：`seq` 是"顺序可追踪"的关键。插入时在同一事务内取 `MAX(seq)+1`；
高并发下建议后续在 `conversation` 增加计数器字段取号（本期未加）。

### 3.6 `conversation_party` 会话人员资料表

| 字段 | 类型 | 说明 |

### 3.8 `ocr_record` OCR 识别记录表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | PK |
| image_id | BIGINT UNSIGNED | 材料 |
| provider | VARCHAR(32) | 服务商，当前可为 `MOCK` |
| ocr_type | VARCHAR(40) | 行驶证 / 身份证 / VIN |
| status | VARCHAR(20) | `PENDING` / `SUCCESS` / `FAILED` |

### 3.9 `insurance_plan` 保险方案表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | PK |
| conversation_id | BIGINT UNSIGNED | 会话 |
| order_id | BIGINT UNSIGNED | 下单后回填，可空 |
| previous_plan_id | BIGINT UNSIGNED | 上一版本，首版 NULL |
| version | INT | 版本号 |
| insurer_code / insurer_name | VARCHAR | 保险公司 |
| source | VARCHAR(20) | `AI` / `MANUAL` / `TEMPLATE` |
| status | VARCHAR(20) | `DRAFT` / `PENDING_CONFIRM` / `CONFIRMED` / `REJECTED` / `SUPERSEDED` |
| estimated_total | DECIMAL(12,2) | 预估总保费，未知 NULL |

## 4. 订单状态机

```text
CREATED → QUOTING → QUOTED → UNDERWRITING → UNDERWRITTEN → PENDING_PAYMENT → PAID → ISSUING → ISSUED
   │          │         │           │                                              │
   ▼          ▼         ▼           ▼                                              ▼
CANCELLED  FAILED    FAILED     FAILED                                          FAILED
                                  └—— 补件后重新核保 ——▶ UNDERWRITING
```

**Service 层必须校验**：

1. 只能按相邻状态推进，禁止跳级（如 `CREATED` 直接 `PAID`）。
2. `PAID` 只能由支付回调/查单触发。
3. `ISSUED` 只能在保单落库后设置。
4. 每次变更必须同事务写 `order_status_log`，并校验 `version`。
5. 终态 `ISSUED` / `CANCELLED` / `FAILED` 不再变更。

## 5. JSON 字段说明

| 表.字段 | 为什么用 JSON | 边界 |
| --- | --- | --- |
| `chat_message.metadata` | 卡片、工具调用结构随场景变化 | 不存业务主数据 |
| `ocr_record.structured_result` | 证件类型不同、服务商可能更换 | 确认后写正式列 |
| `insurance_plan_item` 无 JSON | 险种是独立行 | — |
| `underwriting_record.required_materials` | 补件要求是动态数组 | 一期够用 |
| `quote_record.response_summary` | 第三方响应结构不稳定 | 仅留痕 |
| `payment_record.callback_payload` | 回调原文格式由平台决定 | 脱敏后存 |
| `insurance_order.*_snapshot` | 必须冻结下单时的数据 | 订单核心字段仍是独立列 |
| `policy.details` | 保单特别约定、险种明细 | 二期可拆 `policy_item` |

**原则**：金额、状态、版本、业务编号、关联 ID 一律独立成列，可索引、可聚合、可校验；
JSON 只承载"结构不稳定、只做展示或留痕"的数据。

## 6. 敏感数据与权限

| 数据 | 存储 | 查询 | 展示 |
| --- | --- | --- | --- |
| 密码 | BCrypt `password_hash` | 不可逆校验 | 永不返回 |
| 身份证号 | AES-256-GCM `id_no_cipher` | `id_no_hash` 精确匹配 | 只返回 `id_no_masked` |
| 发动机号 | AES-256-GCM `engine_no_cipher` | — | 只返回 `engine_no_masked` |
| 支付回调 | 脱敏后存 `callback_payload` | — | 不返回前端 |

**密钥**：用环境变量 `PII_AES_KEY`、`PII_HMAC_KEY` 注入，不入库、不入代码、不入 Git。

**权限**：客户只看自己的数据；业务员只看自己接待的会话与订单；管理员可查全部，
但敏感字段默认脱敏。

## 7. 索引策略

1. 关联字段全部建索引（`*_id`）。
2. 列表页按"用户 + 时间"建联合索引，如 `(customer_id, created_at)`。
3. 状态 + 时间组合：`(status, requested_at)`、`(order_id, status)`。
4. 业务编号唯一索引，兼作幂等保护。
5. 不为低选择性字段单独建索引（如 `deleted`）。

| 维度 | 旧版 v0（docs 原稿） | 本版 v1（17 表） |
